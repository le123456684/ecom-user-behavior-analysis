## 第 0 步 · 先搞清楚数据长什么样

在动手之前，必须先知道手里有什么。这个项目有 **4 张表**：

| 表名 | 类型 | 一行代表什么 | 行数 |
|---|---|---|---|
| `user_behavior` | **事实表** | 某个用户，在某个时间，对某个商品，做了一次什么行为 | 516,322 |
| `user_dim` | 维度表 | 一个用户的档案（首访日、末访日、活跃天数、总浏览数、总购买数） | 20,000 |
| `item_dim` | 维度表 | 一个商品的档案（属于哪个类目） | 2,000 |
| `date_dim` | 维度表 | 一天的时间属性（第几周、周几、是否周末） | 30 |

**事实表 + 维度表** 是数仓最基础的建模思想（星型模型）：

- **事实表**存「发生过的事」，行数最多，会持续增长
- **维度表**存「事物的属性」，行数稳定，用来给事实表「贴标签」

为什么要有 `date_dim`？因为「是否周末」这种属性，写在 SQL 里就是 `CASE WHEN isoweekday >= 6`，但放到维度表里，
业务同事改口径时不用碰 SQL —— 这是**维度建模**的核心价值。

> **面试点**：「你们的数据是怎么建模的？」→ 答「事实表 + 维度表，事实表存行为流水，维度表存用户/商品/日期属性，分析时通过 join 补充上下文」。

## 第 1 步 · `01_generate_data.py` —— 造数据

### 它在干什么

程序化生成 30 天、2 万名用户的完整行为流水，写成 4 个 CSV。

### 三个关键设计（这才是重点，不是代码本身）

#### 设计 1：用户分层 —— 让数据「像真的」

真实电商的用户不是均匀分布的：少数人疯狂买，多数人偶尔逛。代码里用 5 档分层模拟：

| 分层 | 占比 | 每天行为数 | 次日活跃概率 | 购买概率 |
|---|---|---|---|---|
| A-高频购买 | 1.5% | 15–35 次 | 0.75 | 12% |
| B-有过购买 | 5% | 10–26 次 | 0.65 | 3% |
| C-高活跃浏览 | 18% | 8–22 次 | 0.55 | 0.1% |
| D-一般活跃 | 45% | 4–12 次 | 0.45 | 0.04% |
| E-低活沉默 | 30.5% | 1–5 次 | 0.25 | 0.01% |

```python
TIERS = [
    ("A-高频购买",   0.015, (15, 35), 2.4, 0.75, 0.97, (0.58, 0.09, 0.14, 0.120)),
    ("B-有过购买",   0.050, (10, 26), 1.9, 0.65, 0.93, (0.65, 0.10, 0.13, 0.030)),
    #  ...
]
```

> **为什么重要**：如果所有用户行为强度一样，最后的分析结论会是「所有类目转化率都差不多」——
> 看不出任何洞察。**分层是为了让分析有东西可挖。**

#### 设计 2：类目差异化 —— 埋下「机会点」

10 个类目各自配了流量权重和转化系数，故意做出两种极端：

```python
(3,  "数码电子",  0.20, 0.45, 0.65),   # ← 高流量 · 低转化（核心机会点）
(7,  "美妆个护",  0.13, 1.55, 1.35),   # ← 中流量 · 高转化
(9,  "家居家装",  0.04, 1.95, 1.60),   # ← 低流量 · 高转化（小众高潜）
```

数码电子吃掉 20% 流量但转化系数只有 0.45，最后必然被分析成「高流量低转化」的优化靶子 ——
**这是设计出来的结论，不是碰巧发现的。**

> **面试点（重要）**：面试官可能问「这个项目的数据是真实的吗？」
> **必须诚实回答**：数据是模拟生成的，但**生成逻辑刻意贴近真实电商特征**，分析方法和结论逻辑与真实项目一致。
> 如果含糊其辞说是真实数据，被追问一句「数据从哪个平台来的」就崩了。

#### 设计 3：留存衰减 —— 模拟注意力流失

第一版数据有个 bug：用户的活跃日被均匀撒在 30 天里，导致留存曲线是平的（D1 34.7% → D7 29.5%）。
真实用户不会这样 —— **人会腻**。改成按衰减概率激活：

```python
active = [first]
for off in range(first + 1, DAYS):
    if random.random() < base_p * (decay ** (off - first)):   # 每过一天，回来的概率乘 0.65~0.97
        active.append(off)
```

修正后 D1 34.15% → D7 11.47%，曲线正常衰减了。

> **面试点**：「你怎么判断数据有没有问题？」→ 举这个例子：**留存曲线不衰减，通常不是业务好，是数据有问题。**

### 最容易忽略的一行

```python
local = datetime.datetime(d.year, d.month, d.day, hour, ...)
ts = int(local.timestamp())     # ← 这一行
```

`timestamp()` 会**自动按本机时区**把本地时间转成 UTC 纪元值。
我最初在生成侧手动减了 8 小时，又在下游 SQL 里加了 8 小时 → **负负得正，等于没换算**，峰值时段依然错在 12–14 点。

> **面试点**：这是最能体现「你真跑过」的细节。别人只能背「要注意时区」，你能讲出「双重偏移」这个具体坑。

## 第 2 步 · `02_build_db.py` —— 建库

### 它在干什么

删旧库 → 建 4 张表 → 灌数据 → **建 5 个索引** → **数据体检**。

### 为什么建这 5 个索引

索引不是越多越好（占空间、拖慢写入）。这 5 个是**按下游查询反推出来的**：

| 索引 | 服务于哪个查询 |
|---|---|
| `idx_ub_dt` | 按天聚合（日活趋势） |
| `idx_ub_beh` | 按行为类型筛选（漏斗） |
| `idx_ub_cat` | 按类目分组（类目分析） |
| `idx_ub_user` | 按用户分组（留存、分层） |
| `idx_ub_dt_beh` | **复合索引**：`WHERE dt BETWEEN ... AND behavior_type=...` |

最后那个是**复合索引**，因为最常出现的查询模式是「某段时间 + 某类行为」，把两列建在一起比建两个单列索引更有效 ——
这是数据库优化的基本功。

> **面试点**：「索引怎么建的？」→ 不要答「给每列都建」，要答「按查询模式建的，最常用的是 `(dt, behavior_type)` 复合索引」。

### 数据体检 —— 最少被重视、最容易被追问的一环

```python
# 检查 1：有没有重复记录
SELECT COUNT(*) FROM (
  SELECT user_id,item_id,behavior_type,ts FROM user_behavior
  GROUP BY user_id,item_id,behavior_type,ts HAVING COUNT(*)>1
)

# 检查 2：有没有「孤儿记录」（事实表里的商品在维表里找不到）
SELECT COUNT(*) FROM user_behavior b
LEFT JOIN item_dim i ON b.item_id = i.item_id
WHERE i.item_id IS NULL
```

| 检查 | 发现的典型问题 | 为什么要查 |
|---|---|---|
| 重复记录 | 埋点重复上报、ETL 重跑导致的数据翻倍 | 会虚高所有计数指标 |
| 孤儿记录 | 商品被删除但历史行为还在 / 埋点维度丢失 | join 时会丢数据，导致类目统计不全 |

> **面试点（高频）**：「你怎么保证数据质量？」→ 这两条就是标准答案的骨架：
> **查重复、查维表关联完整性**，顺便说一句「如果这两项不干净，后面所有指标都不可信」。

## 第 3 步 · `03_analyze.py` —— 分析（核心，占全场 70% 分量）

跑 **6 个分析任务**，每个任务的结果存一份 CSV。逐个讲：

### 任务 2：流量与时段

**2.1 日活与流量总览**

```sql
SELECT dt,
       COUNT(DISTINCT user_id) AS uv,
       SUM(behavior_type='pv') AS pv,
       ROUND(SUM(behavior_type='pv')*1.0/NULLIF(COUNT(DISTINCT user_id),0), 2) AS pv_per_uv,
       COUNT(DISTINCT CASE WHEN behavior_type='buy' THEN user_id END) AS buy_uv
FROM user_behavior GROUP BY dt ORDER BY dt
```

三个考察点：

- `COUNT(DISTINCT user_id)` → **UV 必须去重**，同一个用户一天看 10 次只算 1 个人
- `SUM(behavior_type='pv')` → 这是个简写技巧：条件成立返回 1，求和等于计数。等价于 `COUNT(CASE WHEN ... THEN 1 END)`
- `pv_per_uv` → **人均浏览深度**，衡量流量质量。UV 高但人均深度低 = 来了就走，是无效流量

**2.2 时段分布（时区陷阱就在这）**

```sql
SELECT CAST(strftime('%H', ts + 28800, 'unixepoch') AS INTEGER) AS hour_of_day,
       SUM(behavior_type='pv') AS pv,
       ROUND(SUM(behavior_type='pv')*100.0/SUM(SUM(behavior_type='pv')) OVER (), 2) AS pv_share_pct
FROM user_behavior GROUP BY hour_of_day
```

- `ts + 28800` → **+8 小时**把 UTC 转成北京时间。不加这一句，你算出的高峰是 12–14 点（错的）
- `SUM(...) OVER ()` → **窗口函数**，算「占全天的百分比」。这是 JD 里写「SQL 进阶」时要的东西

> **结论**：20–22 点占全天 30.8% 的浏览量，峰值 21 点。→ 运营投放应该集中在这个时段。

**2.3 周末 vs 工作日**

用子查询先算出「每天」的 UV/PV，再 join 日期维表，按是否周末分组求平均。
考察的是**两层聚合**的写法：先按天聚合，再按周末/工作日聚合。

> **结论**：周末人均浏览 8.03 次 vs 工作日 7.01 次（+14.6%）。

### 任务 3：转化漏斗（本项目的核心产出）

**3.1 全局漏斗 —— 一段 SQL 算四层人数**

```sql
SELECT
  COUNT(DISTINCT CASE WHEN behavior_type='pv'   THEN user_id END) AS browse_users,
  COUNT(DISTINCT CASE WHEN behavior_type='fav'  THEN user_id END) AS fav_users,
  COUNT(DISTINCT CASE WHEN behavior_type='cart' THEN user_id END) AS cart_users,
  COUNT(DISTINCT CASE WHEN behavior_type='buy'  THEN user_id END) AS buy_users
FROM user_behavior
```

**这是整个项目最值得讲的一段 SQL。** 拆开看：

| 写法 | 含义 | 为什么这么写 |
|---|---|---|
| `COUNT(DISTINCT ...)` | 数「有多少人」 | 漏斗衡量的是人，不是次数 |
| `CASE WHEN ... THEN user_id END` | 只在满足条件时返回 user_id，否则返回 NULL | 关键技巧：`ELSE` 不写就是 NULL，NULL 被 COUNT 自动忽略 |
| 四个写在一个 SELECT 里 | 一次扫描全表 | 写四个子查询要扫四遍，**性能差 4 倍** |

> **面试点（必被问）**：「为什么不用四个子查询？」→
> 答「四个子查询意味着四次全表扫描；用条件聚合一次扫描就能出四个指标。
> 数据量上亿时这个差异是数量级的」。这个回答能直接拉开档次。

**3.2 逐层流失率**

用 CTE 把 3.1 的结果存起来，再用 `UNION ALL` 拼成漏斗表：

```sql
WITH f AS ( /* 3.1 的四个数 */ )
SELECT '浏览' AS step, s1 AS users, 100.00 AS rate_pct, NULL AS drop_pct FROM f
UNION ALL SELECT '收藏', s2, ROUND(s2*100.0/s1,2), ROUND((s1-s2)*100.0/s1,2) FROM f
UNION ALL SELECT '加购', s3, ROUND(s3*100.0/s2,2), ROUND((s2-s3)*100.0/s2,2) FROM f
UNION ALL SELECT '购买', s4, ROUND(s4*100.0/s3,2), ROUND((s3-s4)*100.0/s3,2) FROM f
```

- **CTE（`WITH ... AS`）** 的作用：把复杂查询拆成有名字的步骤，可读性远好于嵌套子查询；且 CTE 只算一次
- `NULLIF(x, 0)` 的作用：分母为 0 时返回 NULL 而不是报错/返回 0。**返回 0 会污染后续平均值计算**

> **结论**：漏斗 19,816 → 9,053 → 7,926 → 1,511。
> **最大流失在「加购→购买」，流失 80.94%** —— 用户已经加购（强意向）却不买，问题在成交链路。

**3.4 / 3.5 类目漏斗 + 机会点识别**

```sql
GROUP BY category_id
HAVING browse_u >= 100        -- ← 样本量门槛
```

`HAVING` 这里的作用不是过滤数据，是**过滤统计噪音**：
一个只有 5 个人逛的类目，恰好 1 个人买了 → 转化率 20%，会排到第一名，直接误导选品决策。

3.5 再用窗口函数算「全站均值」，找出**转化率低于全站均值、且流量占比 > 2%** 的类目 —— 这就是优先级最高的优化靶子。

> **结论**：数码电子，15.04% 流量、4.54% 转化，低于全站 5.72%，缺口 1.18pp。

### 任务 4：行为路径

```sql
WITH s AS (
  SELECT user_id, behavior_type, ts,
         LAG(behavior_type) OVER (PARTITION BY user_id ORDER BY ts) AS prev
  FROM user_behavior
)
SELECT prev AS from_step, behavior_type AS to_step, COUNT(*) AS transitions
FROM s WHERE prev IS NOT NULL
GROUP BY from_step, to_step ORDER BY transitions DESC
```

**`LAG()` 窗口函数**：取「同一用户、按时间排序后的上一行」。
`PARTITION BY user_id` 保证不跨用户乱取（否则会把 A 用户的最后一步和 B 用户的第一步连起来）。

用途：
- **行为转移矩阵**：用户在什么行为之后最可能买？（回答：加购之后）
- **购买前一步分布**：直接买 vs 加购后买，各占多少 → 决定要不要主推「加购」这个动作

> **面试点**：`LAG`/`LEAD` 是「路径分析 / 会话分析」的标准工具，电商、内容平台都高频使用。

### 任务 5：留存

**5.1 次日留存**

```sql
WITH fd AS (SELECT user_id, MIN(dt) AS reg_dt FROM user_behavior GROUP BY user_id),
     act AS (SELECT DISTINCT user_id, dt FROM user_behavior)
SELECT f.reg_dt,
       COUNT(DISTINCT f.user_id) AS new_users,
       COUNT(DISTINCT CASE WHEN julianday(a.dt)-julianday(f.reg_dt)=1 THEN a.user_id END) AS retained_d1
FROM fd f LEFT JOIN act a ON f.user_id = a.user_id
GROUP BY f.reg_dt
```

留存的标准套路，三步：

1. **找每个人的「首访日」**：`MIN(dt) GROUP BY user_id`
2. **找每个人的「活跃日」**：`SELECT DISTINCT user_id, dt`（注意要去重，一天多次活跃只算一天）
3. **自关联后算天数差**：`julianday(a.dt) - julianday(f.reg_dt) = 1` 就是次日留存

> **为什么用 `LEFT JOIN` 而不是 `JOIN`**：LEFT JOIN 保证首访用户即使第二天没来也会出现在结果里（分子为 0），
> 用 JOIN 会把这些用户整个丢掉，**导致留存率虚高**。这是个很容易踩的坑。

**5.2 留存矩阵（同期群 Cohort 分析）**

按「注册日」把用户分成一个个同期群，看每个群在第 0/1/2/3/7 天的留存率：

```sql
WHERE co.reg_dt <= '2025-11-23'     -- ← 只统计「观察窗口完整」的同期群
```

这一行非常关键：11 月 25 日注册的用户，到数据结束（11 月 30 日）只有 5 天可观察，
强行算 D7 留存会被低估 —— 这叫**观察窗口不完整**，必须剔除。

> **面试点**：「留存分析要注意什么？」→ 答这两点：① 分母必须是同期群人数，不能混；
> ② 观察窗口不完整的同期群要剔除。

**5.3 复购率**

```sql
WITH bc AS (
  SELECT user_id, COUNT(*) AS buy_times FROM user_behavior
  WHERE behavior_type='buy' GROUP BY user_id
)
SELECT COUNT(*) AS buyer_users,
       SUM(CASE WHEN buy_times>=2 THEN 1 ELSE 0 END) AS repeat_buyers,
       ROUND(SUM(CASE WHEN buy_times>=2 THEN 1 ELSE 0 END)*100.0/NULLIF(COUNT(*),0),2) AS repeat_rate_pct
FROM bc
```

**口径必须写清楚**：分母是「有购买行为的用户」，不是「全部用户」。
这两者差很多（7.63% 转化率下，用全部用户当分母，复购率会缩小 13 倍）。

> **面试点**：「复购率怎么定义的？」→ 一定要主动说清楚分子分母，这是口径意识的体现。

**5.4 用户分层**

用 `CASE WHEN` 把用户分成 A/B/C/D/E 五档，再用窗口函数算各档占比。
这是**运营分层触达的基础**：A 档维护、B 档提升、C 档（高活跃不购买）攻坚。

> **结论**：C 档「高活跃浏览」3,439 人（17.20%），逛得多却不买 —— 这是转化攻坚池。

### 任务 6：类目

| 子任务 | 产出 | 用途 |
|---|---|---|
| 6.1 类目流量结构 | 各类目 PV 占比、UV | 看清流量盘子 |
| 6.2 类目转化率排名 | 加 `HAVING browse_u >= 100` 门槛 | 剔除噪音 |
| 6.3 **高流量低转化** | 核心产出 | 找优化机会点 |
| 6.4 **加购未购买** | 再营销人群池 | 找短期可捞的钱 |

6.4 的算法很直接：`加购人数 - 购买人数`，但要注意**这里的人数都是类目内去重**，
加起来得到的 **13,729 人次**是「人 × 类目」口径，不是「人」口径 —— 同一个人可能在多个类目加购过。

> **面试点**：主动说清「13,729 是人次不是人数」，这种口径自觉非常加分。

## 第 4 步 · `04_report.py` —— 出报告

### 它在干什么

把 `results/` 里的 CSV + `summary.json` 读出来，拼成一个 **7 页 A4 的 HTML 报告**。

### 关键技术点：手写 SVG

```python
def chart_daily(w=640, h=230):
    ...
    def path(vals, mx):
        return " ".join(f"{'M' if i == 0 else 'L'}{sx(i):.1f},{pad_t + ch - ch*v/mx:.1f}"
                        for i, v in enumerate(vals))
```

不依赖 matplotlib，直接用字符串拼 SVG 的坐标：

- `M x,y` = 移动到起点，`L x,y` = 画线到下一个点
- `sx(i)` 把第 i 个数据点映射到 X 坐标，`pad_t + ch - ch*v/mx` 映射到 Y 坐标（**Y 轴要翻转**，因为 SVG 原点在左上角）

**好处**：报告是一个单文件 HTML，没有外部图片依赖，直接发给 HR 就能打开，也能一键打印成 PDF。

> **面试点**：如果被问「为什么不用 Tableau」，可以答「正式交付会用 BI 工具，
> 这里手写 SVG 是为了让交付物零依赖、可直接分享」。

### 一个体现严谨性的细节

```python
cart_nb_total = sum(int(r[4]) for r in cart_nb)   # 动态计算，不写死
```

报告里的「13,729 人次」不是硬编码的数字，是**从结果文件里现算的**。
硬编码的数字在数据变动后会变成假数据 —— 这是数据人最容易犯的错。

## 第 5 步 · `05_export_cube.py` —— 导出看板数据（口径陷阱集中地）

### 它在干什么

把看板需要的所有聚合数据算好，导出成一个 JSON。看板前端不碰数据库，只读这个 JSON。

### 核心：去重指标不能跨期相加

这是本项目**最值钱的一个坑**：

```python
RANGES = {
    "all":   (ALL_DATES[0], ALL_DATES[-1]),
    "first": (ALL_DATES[0], ALL_DATES[14]),
    "last":  (ALL_DATES[-15], ALL_DATES[-1]),
}

def distinct_stats(where=""):
    """按行为类型返回区间去重人数 + 计数"""
    sql = f"""
    SELECT behavior_type, COUNT(DISTINCT user_id), COUNT(*)
    FROM user_behavior {where}
    GROUP BY behavior_type
    """
```

**做法**：对每个固定区间（全期 / 前 15 天 / 后 15 天），**单独跑一次 `COUNT(DISTINCT)`**，
而不是把日粒度的 UV 加总。

**错误做法的后果**（脚本最后会打印出来对照）：

```
全期独立访客（正确）      : 19,816
日 UV 简单相加（错误做法）: 53,570   ← 差 33,754
真实转化率（正确）        : 7.63%
用相加值算的转化率（错误）: 2.82%
```

**根因**：`COUNT(DISTINCT user_id)` 是 **非加法指标（non-additive measure）**。
一个用户活跃 5 天，在 5 个日期分组里各被计 1 次，相加等于 5，但真实只有 1 个人。

**哪些能加、哪些不能加**：

| 指标类型 | 例子 | 能否跨维度相加 |
|---|---|---|
| 计数型（additive） | PV、订单数、加购次数 | ✅ 可以安全相加 |
| 非加法（non-additive） | UV、独立访客、去重人数 | ❌ 必须重新去重计算 |
| 半加法（semi-additive） | 库存、余额 | ❌ 跨时间不能加，跨门店可以 |

> **面试点（王牌）**：这是能让面试官眼睛一亮的回答。
> 大部分候选人只会说「UV 要去重」，你能说出「DISTINCT 类指标跨维度汇总时必须重算，
> 因为它是 non-additive measure」，并给出 53,570 vs 19,816 的实测差距 —— 层次完全不同。

### 为什么日粒度数据仍然有用

```python
# 类目日粒度（只取 pv 计数，加法安全）
cur.execute("""SELECT dt, category_id, SUM(behavior_type='pv')
               FROM user_behavior GROUP BY dt, category_id""")
```

日粒度的 UV 是**当日去重**，用于画趋势图是正确的；只有「跨日加总」才是错的。
所以脚本里对日粒度只保留 PV 这类可加指标。

## 第 6 步 · `06_build_dashboard.py` —— 出看板

### 它在干什么

把 JSON 数据嵌进 HTML 模板，生成一个**可交互**的看板。

### 核心技术：数据一次嵌入，前端实时重算

```python
D = json.dumps(cube, ensure_ascii=False, separators=(",", ":"))
HTML = f'''<!DOCTYPE html>...'''
```

把整个数据立方（cube）序列化后写进 HTML 的 `<script>` 里。
用户切换筛选条件时，**JavaScript 在浏览器里重新计算**，不请求服务器。

**代价与取舍**：数据量必须小（这里 JSON 只有 9 KB）。如果数据量大（比如几十万行明细），
就必须改成后端接口按需查询 —— **这就是「静态看板」和「BI 平台」的分界线**。

> **面试点**：「你这个看板能支持多大数据量？」→ 答「当前是静态嵌入，适合聚合后的小数据；
> 如果是明细级、数据量大，需要改成后端 API + 前端按需查询」。

### 内置口径纠错演示

uv_wrong = sum(v["pv"]["u"] for v in cube["daily"].values())
conv_wrong = buy_true / uv_wrong * 100

## 三、面试速查卡（背下来）

**Q：介绍一下这个项目**
> 这是一个电商用户行为的全链路分析项目，51.6 万条行为流水、2 万用户、30 天。
> 我用 SQL 完成了从建库到分析的全流程，重点做了三件事：
> 转化漏斗定位流失环节、留存分析看用户质量、类目分析找优化机会点。
> 最后产出两份交付物：一份 7 页的分析报告和一个可交互的看板。

**Q：最关键的发现是什么**
> 转化率 7.63%，但漏斗里「加购→购买」流失了 80.94%，这是最大的瓶颈。
> 同时数码电子占 15% 流量但转化只有 4.54%，低于全站均值 —— 这两个是优先级最高的优化点。

**Q：用了哪些 SQL 技巧**
> 条件聚合（`COUNT(DISTINCT CASE WHEN)`）一次扫描算四层漏斗；
> CTE 拆解多步逻辑；`LAG` 窗口函数做路径分析；`OVER()` 算占比和全站均值；
> `NULLIF` 保护分母；`HAVING` 过滤统计噪音。

**Q：遇到过什么问题（这题的答案最见功底）**
> 三个：① 时区双重偏移导致高峰时段定位错了 8 小时；
> ② 去重人数跨期相加，导致访客数虚高 2.7 倍、转化率算错；
> ③ 第一版模拟数据的留存曲线不衰减、转化率高达 37%，做常识校验时发现是数据本身不合理。

**Q：数据是真的吗**
> 数据是模拟生成的，但生成逻辑刻意贴近真实电商特征（用户分层、类目差异、时段规律、留存衰减）。
> 分析方法、指标口径和结论逻辑与真实项目完全一致。
